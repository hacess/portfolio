How this works
  1. Knowledge base. My resume, case studies and project notes are split into ~40 small chunks in data/knowledge.json, each tagged with the section it came from.
  2. Guardrails first. Questions are length-capped, and anything that looks like an instruction ("ignore previous…", "reveal your prompt") is treated as data and politely declined.
  3. Retrieval. The question is tokenized, stemmed and expanded with a small synonym map, then ranked with BM25 in your browser.
  4. Relevance threshold. Chunks below a minimum score are dropped. If nothing survives, I say I don't know instead of guessing.
  5. Extractive answer. The reply is built only from sentences I wrote, never generated, and every answer links its sources.

It's the same principle I use in production RAG systems (controlled retrieval, grounded context, cite or abstain), taken to the extreme: no model, no API key, no cost, and nothing to hallucinate.

    Case studies

    case/01 · llm · rag

    LLM and RAG pipeline for very large document sets

    Problem

    Legal-style cases arrive as huge bundles of scanned and digital documents, up to 45,000+ pages per case. Off-the-shelf chat tools hit file-size limits and answered without grounding, so reviewers couldn't trust the output.

    Constraints

    • No practical file-size ceiling; mixed scanned and native PDFs.
    • Answers must be traceable to source pages.
    • Sensitive documents: data stays inside our own infrastructure and providers.
    • Output must be structured (summaries, briefs, strategy notes), not free chat.

    Key decisions

    • pgvector inside PostgreSQL instead of a separate vector store, so chunks, metadata and embeddings share one transactional database (see the decision log).
    • OCR → parse → chunk → embed as a pipeline of resumable steps, so a 45,000-page case can be processed without file-size limits.
    • Page-level metadata on every chunk, so every answer can cite where it came from.
    • Provider-agnostic LLM layer via LangChain, so Claude or Gemini can be used per task.

    Outcome

    Full cases up to 45,000+ pages can be queried and turned into case summaries, structured briefs and strategy notes, with noticeably fewer hallucinations than a general-purpose chat interface.

    case/02 · reliability · prompts

    Reducing hallucinations with structured prompts and controlled retrieval

    Problem

    Even with retrieval in place, a single "here is some context, answer the question" prompt produced confident answers that weren't supported by the documents. In a document-heavy domain that's worse than no answer.

    Constraints

    • Users need to verify every claim quickly.
    • Saying "not found" is acceptable; inventing facts is not.
    • Must work across more than one LLM provider.

    Key decisions

    • Controlled retrieval: relevance thresholds and metadata filters, so weak matches never reach the prompt.
    • Structured prompt pipeline: break the task into steps with fixed output schemas instead of one open-ended prompt.
    • Context-only instructions: the model is told to answer only from supplied chunks and to say when information is missing.
    • Citations and validation: outputs must reference source chunks and match the schema before they reach the user.

    Outcome

    Hallucination issues were reduced compared with standard LLM interfaces through RAG-based grounding and prompt engineering.

    The chat on this page uses the same principle in miniature: retrieve, threshold, cite, or abstain.

    case/04 · open source · side projects

    Chrome extensions (Manifest V3) and the Kairo desktop pet

    Problem

    Chrome's Manifest V3 moved extensions to service workers and stricter APIs, which broke many older screenshot tutorials. Separately, I wanted a small, friendly desktop companion for break reminders that doesn't need an account or send data anywhere.

    Constraints

    • MV3: no persistent background page; work within service-worker lifetimes.
    • Full-page capture across very different page layouts.
    • Kairo Lite: cross-platform (macOS, Windows, Linux), local-first, no telemetry.

    Key decisions

    • Scroll and stitch: capture viewport by viewport and stitch into a single PNG, rather than relying on unsupported full-page APIs.
    • Teach the fundamentals: keep the repos small and readable so they double as Manifest V3 tutorials.
    • Kairo Lite on Electron with everything read locally (idle time, battery, CPU) and config in one JSON file; window-climbing is an optional native module, so the app still runs if it fails to build.

    Outcome

    The two screenshot extensions have 15 stars each on GitHub, and Kairo Lite ships as a free cross-platform app. The mascot on this page is a nod to Kairo.

    Decision log

    Short architecture decision records: why I chose X over Y.

    ADR-001

    Why I chose pgvector over a dedicated vector database

    Context
    RAG over per-case document sets, where chunks need rich metadata filters (document, page, type) and must stay consistent with the source records.
    Decision
    Store embeddings in PostgreSQL with pgvector, next to documents and metadata.
    Why
    One transactional store; SQL filters and joins with vector search in one query; no second system to run, secure, back up or keep in sync; and the scale fits comfortably.
    Trade-off
    A specialized vector DB can scale further and tune ANN indexes more finely. I'd revisit if the corpus grows by orders of magnitude or needs cross-tenant search.

    ADR-002

    Why I chose cache-aside Redis over write-through caching

    Context
    Read-heavy endpoints and expensive computed results in a SaaS backend.
    Decision
    Cache-aside in Redis with explicit TTLs per key family, plus invalidation when the underlying data changes.
    Why
    The database stays the source of truth; only data that's actually read gets cached; and if Redis is unavailable the app degrades to slower, not broken.
    Trade-off
    The first read after expiry is slow, and invalidation has to be designed carefully to avoid stale data.

    ADR-003

    Why I chose Flask services alongside Laravel over a single stack

    Context
    Products that combine standard business features with LLM, embedding and OCR workloads.
    Decision
    Laravel for core product features; Python (Flask) microservices for AI and document processing.
    Why
    Python has the strongest ecosystem for LLM, embedding and document work; Laravel is very productive for auth, admin and business logic; separate services scale and deploy independently.
    Trade-off
    Two stacks to maintain and a network boundary to design (contracts, retries, observability).

    ADR-004

    Why I chose an on-device model over a cloud API for activity classification

    Context
    A cross-platform Electron app that classifies workforce activity every 60 seconds on every monitored desktop.
    Decision
    A layered pipeline: deterministic app lookup first, and only then a small Qwen 0.8B ONNX vision model, running in a dedicated worker thread, to classify screenshots.
    Why
    Most activity is resolved by the cheap lookup; the model runs locally, so there is no per-call API cost or network round trip for screenshots; and the worker thread keeps the app responsive.
    Trade-off
    A small local model is less capable than a large hosted one, and it adds download size and CPU load on the client.

    ADR-005

    Why I chose a store-and-forward buffer and an alert state machine over plain threshold alerts

    Context
    A solar plant monitoring system streaming inverter and weather telemetry from Modbus RTU through MQTT, where broker disconnects and transient faults are normal.
    Decision
    An async MQTT gateway with a store-and-forward ring buffer persisted to JSONL, and anomaly detection as a 5-state machine (Normal → Detecting → Confirmed → Diagnosed → Recovering) with LLM root-cause diagnosis and a 30-minute cooldown.
    Why
    The buffer means zero data loss during broker disconnections; the confirmation states filter out transient spikes; the cooldown prevents alert storms; and the LLM is only asked about confirmed anomalies.
    Trade-off
    Alerts arrive slightly later while an anomaly is being confirmed, and the buffer needs disk space during long outages.
